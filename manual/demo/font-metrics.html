一支字有幾條線

一支 CJK 字型身上，量得到 五套上下界，而瀏覽器排版只讀其中兩套。 這一頁把它們照真實比例畫出來，然後回答那個真正的問題：哪幾條必須統一，哪幾條不能。

head · hhea · OS/2 · BASE

同一支字，五套上下界

下面這張是尚古明體（思源宋血統，ziano 出貨版）的真實度量， 1em 就是那個青色方框。撥掉幾層看看——同一個字身上疊著五組互不相干的數字。

為什麼「五套」而不是三套：hhea 與 OS/2.usWin* 是兩張表寫同一件事（macOS 讀前者、Windows 讀後者， 我們兩家一律寫成相同值，所以圖上是一條線）；sTypo* 是第三套；BASE 的 ideo／icfb／icft 是第四套；head.yMin/yMax 是第五套。再加上 sxHeight／sCapHeight 兩條給西文用的水平線。
the two knobs

整件事的關鍵：那兩個數字管兩件不相干的事

hhea 只有 ascent 與 descent 兩個數字，但瀏覽器從它們身上取兩個不同的量。 一個必須跟別人一致，另一個絕對不能。

差 決定字在框裡的位置

(ascent − |descent|) / 2 ＝ 中央基線

直排時，字符在欄內的左右位置由它決定。Chromium 與 Safari 都拿「實際畫這個字的那支字型」的 hhea 現算， 減掉行首那支字型（strut）的同一個量。

兩支字型的差不同 → 同一欄裡的字各站在不同的水平位置。

必須全家族統一

和 決定那一行有多高

ascent + |descent| ＋ lineGap ＝ line-height: normal

行框是那一行上所有字型的聯集（union）。同時它也決定 text-emphasis 著重號預留的空間。

和變大 → 沒寫 line-height 的頁面整份鬆開；一顆標點的和太大 → 它會把整行撐高。

各憑角色，不能統一
一句話 同一組 hhea 數字，差要對齊全世界，和要各自為政。 三次調査兜出來的所有結論，都是這一句話的推論。
差 · vertical central baseline

差錯了：直排整欄的字左右錯開

上游三支字型的差散在三個地方。同一欄裡混排明體與楷體，每個字就落在不同的水平位置—— 看起來像「楷體偏左」，其實是兩支字的 hhea 差在打架。

為什麼分片字型一定踩到：帶 unicode-range 的 @font-face 永遠當不上行首那支字型。 實測同一支尚古明體，不加 unicode-range 完美置中，加了就跳 11px。ziano 與 DTJ 每個家族都是分片，所以永遠走這條路。
和 · line box union

和錯了：一顆標點撐大整行

行框是聯集。一支只提供標點的字型若帶著 1.44em 的和， 那一行明明只借它一顆「，」，整行卻被撐到 1.44em。

measured · fontTools

三家出貨檔的實測數字

青色 ＝ 三家一致，朱色 ＝ 刻意不同。看那條加了記號的列：中央基線三家分毫不差。

ziano/src/ziano/metrics.py

那為什麼 ziano 不直接抄 Hiragino 的 0.880／0.120？

因為抄過去差一樣是 0.380（直排照樣對齊），但和會從 1.44 掉到 1.00—— 所有沒寫 line-height 的頁面會突然縮排三成。

所以兩支字取不同的 hhea 不是漏掉

是同一條規則在兩種角色下的兩個解。ziano 是設定行的正文字型，它得保留寬鬆的 normal 行高； DTJ 是加入別人的行的標點字型，它必須降到字身框，才不會撐大人家的行。 該對齊的那一項（差）已經對齊到小數第三位，不該對齊的那一項（和）刻意分開。

還有一個容易漏的細節：ziano 的 cssgen.py 仍然照著同一組常數輸出 ascent-override: 110%; descent-override: 34%。那不是備援，是讓 CSS 與字體檔不可能各說各話—— 同一個常數推導出來的兩份寫法。Safari 那條路徑不吃這個 descriptor，所以真正生效的是字體檔那一份。

head.yMin / yMax

DTJ 的墨跡跨了 2.86em——那不是毛病

全字型的墨跡包絡：ziano −0.220…+0.880，Hiragino −0.297…+1.229， 而 DTJ −1.050…+1.810。追下去，兇手只有兩顆字符。

BASE · DefaultIndex

三次調査下來，唯一還站著的差異

BASE 表的預設基線標籤：Hiragino 全族寫 romn（西文基線）， ziano 與 DTJ 寫 ideo（表意基線）。

今天沒有後果——Chromium 與 WebKit 都還沒把 BASE 接到 CJK 的 dominant-baseline， 直排中央基線走的是前面那條 hhea 合成。但這是「將來會醒過來」的一格： 哪天引擎真的實作了，我們與系統 fallback 就會在混排時各認一條基線。

要不要靠攏 romn，是與系統字對齊跟忠於思源原廠的取捨； 而且動它會牽到 ICF 相關的路徑——Chrome 的 text-spacing-trim 有一道 han_kerning 一致性檢查，是逐 face 跑的。值得單獨量一次再決定。

順帶：兩件已經沒問題但值得記住的事

x-height 隨字重走。Hiragino Sans W0 的 x-height 是 0.520，W9 是 0.590；ICF 框也跟著從 −0.062/+0.822 走到 −0.089/+0.849。那是視覺補償，不是不一致——字重越粗，字面本來就該撐得越滿。 值得記一筆的是 ziano 尚古明的 −0.074/+0.834 正好落在這個區間的中段，介於 W3 與 W6 之間。

ex 讀的是 strut，不是畫字那支。 han 首頁 dash-fuse.css 裡用 translate: -0.5ex 0 抵銷 vertical-align: middle 的那個補償，讀到的是行首那支字型的 x-height，不是 DTJ 的。

Hiragino Sans CNS 這台機器沒有裝（system_profiler 零命中， AssetsV2 的按需字體資產裡也沒有）。它是 macOS 的繁中黑體，屬同一套 Hiragino，照那張表的規律 幾乎確定也是 0.880/0.120——但這一格只能算推定，不是實測。
