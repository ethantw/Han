# 每個節點背多重：han.css 的 token 架構在計算樣式上的代價

**一句話**：首頁的記憶體剩下的那一半不在節點數、不在字體、不在光柵，而在
**計算樣式**——同一棵 DOM，掛上 han.css 之後每個節點的 `blink_gc` 從 4.2 KB
變成 20.4 KB。四個模組佔 104 MB，`han.fonts.css` 一支就 52 MB。

姊妹篇：`2026-08-25-font-fallback-list-memory.md`（字族切片的那一半）。

## 量法

Chrome 的 memory-infra 傾印（`Tracing.requestMemoryDump`，`detailed`），對準
渲染行程的 pid，三輪取最小。`ps` 的 RSS 不能用——它把共用頁面與映射都算進來，
散佈 ±150 MB。

## 同一棵 DOM，只切樣式表

8,684 個節點（其中 3,894 個是 han.js 的 `h-char`／`h-layer` 包裹層）：

| 設定 | blink_gc | 每節點 | 相異字體描述 |
| --- | ---: | ---: | ---: |
| 原樣 | 173 MB | 20.4 KB | 121 |
| 只擋 `han.fonts.css` | 121 MB | 14.2 KB | 85 |
| 只擋 han 四模組 | **69 MB** | 8.2 KB | 57 |
| 只擋頁面自己的樣式 | 160 MB | 18.9 KB | 37 |
| 全擋 | 35 MB | 4.2 KB | 20 |

兩個推論：

**一、不是節點的錯。**節點數一格都沒變，光靠切樣式表就能讓 `blink_gc` 掉
80%。4.2 KB／節點正好落在 apple.com 商品頁的區間（MBP 6 KB、iPhone 17 Pro
8 KB）——我們的 DOM 不比人家貴。

**二、也不是字體描述數的錯。**「只擋頁面自己的樣式」那一列把描述從 121 砍到
37，`blink_gc` 只從 173 掉到 160。所以貴的不是描述的數量，是**每個元素身上
掛著的自訂屬性**：han.css 把三個複合字族 token 宣告在 `:where(*)` 上，逐語言的
`@container style()` 區塊再逐元素重新代換。那是刻意的設計（見
`src/css/fonts.css` 的註解：掛在 `:root` 會把 HanNone 哨兵凍進字串，逐語言的
槽位就再也套不上），而這是它的帳單。

## 對照

| | han 首頁 | apple MBP | iPhone 17 Pro | apple 首頁 |
| --- | ---: | ---: | ---: | ---: |
| private footprint | 336 | 148 | 172 | 254 |
| malloc | 148 | 75 | 74 | **205** |
| blink_gc | **176** | 34 | 50 | 17 |
| 光柵磚 | 92 | **171** | 107 | 52 |
| 節點 | 8,696 | 5,451 | 6,190 | 1,983 |
| 頁高 | 10,212 | 30,857 | 36,060 | 6,096 |

順帶一提：apple 的**首頁**比它的商品頁更貴（254 MB／1,983 個節點），錢在
`malloc` 而不是樣式——那是媒體，不是排版。所以「頁面簡單」與「記憶體便宜」
不是同一件事。

## `if()` 會不會省下來？不會——但它讓重算快一倍

`src/css/fonts.css` 有一條 `TODO(css-if)`：等 CSS Values 5 的 `if()` 到處都有
了，就把「每個模式值一個 `@container` 區塊」收成一條多分支的值。Chrome 147
已經支援（`if(style(--x: y): A; else: B)`，而且如註解所料，條件讀的是**元素
自己**的值），所以可以直接量。

合成頁：8,000 個元素（四語言各 2,000）、129 個自訂屬性、六個槽位＋三個複合
字族，兩種架構產生的計算值**逐語言相同**。

| | A 現況（32 個 `@container`） | B `if()`（0 個） |
| --- | ---: | ---: |
| `blink_gc` | 15 MB | 14 MB |
| 五次全頁重算 | 126 ms | **64 ms** |

**記憶體沒有差**，而且機制上就不該有差：存下來的是每個元素**解算後**的自訂
屬性表，兩種寫法算出同一張表。`if()` 改的是「這個值怎麼挑出來」，不是「存
多少」。

**重算快一倍**是真的（三輪 127/126/126 對 64/77/79）。那正是視窗改尺寸時要做
的工作——這一輪調查最初的症狀就是 resize 卡。但它今天還不能取代 `@container`
矩陣：Safari 與 Firefox 都還沒有 `if()`，兩條路並存等於把這份 CSS 寫兩遍。

## 一個副產品：真正貴的是「元素彼此不一樣」

那個合成頁還揭穿一件事：129 個自訂屬性 × 8,000 個元素只花 15 MB，而真實頁面
同一個量級花 173 MB——差 11 倍。所以**成本不是自訂屬性的數量**。差別在合成頁
的 8,000 個 `<p>` 幾乎全同，Blink 共用同一份 ComputedStyle；真實頁面每個元素
命中的規則組合都不同，共用不了，於是各背一份。

這也回頭說明為什麼「減少自訂屬性」不會是有效的一刀，而「讓元素更像」不是一個
可以下的指令。

## 藏起來的節點幾乎是免費的——直到有人問它的樣式

`display: none`、`hidden` 屬性（UA 樣式表就是 `display: none`）、
`content-visibility: hidden`、搬進 `<template>`——**四者在記憶體上沒有差別**。
拿這一頁四份續版（1,934 個節點、佔 22%）的真實內容量，各三輪取最小：

| 藏法 | blink_gc | footprint | 節點 |
| --- | ---: | ---: | ---: |
| 留在 `<template>` | 155 | 303 | 6,762 |
| `display: none` | 156 | 301 | 7,769 |
| `content-visibility: hidden` | 153 | 299 | 7,769 |
| `hidden` 屬性 | 150 | 300 | 7,769 |
| **完全渲染** | 161 | 319 | 7,769 |

連「完全渲染」都只多 10–20 MB。原因是 Blink 對隱藏子樹的計算樣式是**用到才
算**：節點在那裡，但沒有人問，就沒有那 20 KB。

**於是這篇最重要的一句話是量測紀律**：`getComputedStyle` 會把隱藏子樹的樣式
**當場算出來**。我有一支探針為了數字體描述而遍歷 `document.querySelectorAll('*')`
逐一 `getComputedStyle`——它自己把那 1,934 個隱藏節點變貴了，於是我先量到
「改成 `<template>` 省了 31 MB」。用同一種量法重做（只數節點、不問樣式），
同一批、四輪取最小：303 對 300 MB，**差 3 MB，落在 ±20 MB 的雜訊裡**。

那個改動因此被撤回了：它買到雜訊，卻賣掉「沒有 JS 也能用 `:target` 原地展開
全文」。**探針改變了被觀測的東西**——今天第二次踩到同一類錯（第一次是 `ps` 的
RSS），值得記著。

## 沒做的事

沒有去動 han.css 的 token 架構。可能的方向是「只在語言邊界宣告複合 token」
而不是每個元素——自訂屬性本來就會繼承，元素只有在祖先的解算對它不成立時才
需要自己那一份。但 `@container style()` 的區塊本來就得逐元素評估，能不能省
下來要先量。**這是庫的核心設計，動它之前要有數字。**
