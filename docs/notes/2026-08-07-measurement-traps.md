# 量測方法論的四個陷阱——量到的數字是對的，量的東西是錯的

**日期**：2026-08-07（從已完成的計畫裡打撈出來）

這個專案的許多結論靠 headless-Chrome 量測支撐。以下四則都是**量測本身
壞掉、但數字看起來完全合理**的實例——比量不到還危險，因為會產出可信
的錯誤結論。

## 1. 量擠壓的 harness 自己不能用 `inline-block`

為了整齊排列待測字對，harness 把每組包成 `display: inline-block`。結果
**連前一天已獨立確認會擠的 `。「` 都量到 6em（未擠）**——也就是整個
harness 全程在「擠壓被關掉」的狀態下取值，連裸基線都沒取到。

原因是工作區帳本早就記過的那條：**pair-squeeze 死於原子行內盒**
（`diantenjeom/docs/pair-squeeze-and-markup.md`）。當時把它當成「產品
標記要避開的事」，沒有推論到「**量測用的標記也不能犯**」。

後果留在程式碼裡：`」，` 是否真的回到 1.5em 至今只有機制層的推理、沒有
實測；`SQUEEZE_BEFORE_HANGABLE` 因此收成保守集（十個閉括號 ＋ `、，。．`），
`：；？！︰` 刻意不納入——不是判定它們不需要，是沒有可信的量測支持納入。

**通則：量測頁面的標記要和產品標記一樣受檢。** 任何為了排版方便而套上
去的容器，都可能改變你要量的那個行為。

## 2. `getBBox()` 對 `<text>` 回的是 em 盒，不是 cap height

`<text>` 的 `getBBox().height` 給的是字體的 em 盒（本案 8.33 units），
不是視覺上的 cap height（約 5）。拿它當「字有多高」去算餘裕，會多估
約 3 個單位——版面看起來鬆，數字看起來精確。

## 3. 逐格截圖掃描會把抗鋸齒與位移讀成訊號

為了確認 `font-style: oblique <角度>` 是否連續作用，做過逐 0.5° 的截圖
掃描，結論是「上漆連續、角度有效」。**這個結論是錯的。**

改用 canvas 直接量墨跡剪切之後真相是：`oblique 4deg / 8deg / 10deg /
14deg / 20deg` 與 `italic` **全部都是 41px**，完全相同。Chromium 的合成
斜體在光柵化階段忽略角度——計算值逐格內插，畫出來是二元的。截圖掃描看
到的「連續變化」來自抗鋸齒與版面位移。

**通則：截圖比對量的是「畫面不同」，不是「你要的那個量不同」。** 要量
幾何就直接量幾何（canvas 像素、`getBoundingClientRect`、Range rect），
別讓渲染噪音混進來。

## 4. 邏輯 `inset` 依**元素自己**的書寫模式解析

`inset-inline-start` 這類邏輯屬性，解析時看的是**該元素自己**的
`writing-mode`，不是它容器的。

所以一個 `horizontal-tb` 的絕對定位子元素坐在 `vertical-rl` 的容器裡
時，`inset-inline-start` 是**物理左**——不是直排欄的欄首。標籤會飛出
帶子外被裁掉。

要把橫排子元素定位到直排容器的欄首，只能用**物理** `inset`（或讓子元素
也繼承直排）。原計畫自陳在同一個 session 內第二次踩到同一件事，可見它
違反直覺的程度。

（與工作區帳本那條「直排中央基線讀 hhea」不同族：那是字體度量問題，
這是 CSS 座標系解析問題。）
