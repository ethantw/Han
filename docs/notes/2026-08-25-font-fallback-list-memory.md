# 切片字族 × 相異字級 ＝ 記憶體：Blink 的 fallback list

**一句話**：堆疊裡只要掛著 `unicode-range` 切片的字族，頁面上**每多一種相異
的字體描述**（字族串 × 字級 × 字重 × 字形）就多花約 **1.5–2 MB**；用系統字
時同一件事只要 0.36 MB。首頁 150 種描述，於是這一項就是 240 MB。

## 怎麼量的（以及為什麼先前量錯）

`ps` 的 RSS 在 macOS 上把共用頁面、字體檔映射與 GPU 對映都算進來，同一組
設定重跑散佈達 **±150 MB**——拿它做分層歸因會得到假結論（我用它冤枉過字體
下載量與切片數）。可信的來源是 Chrome 自己的 memory-infra：

```js
await cdp.send('Tracing.start', {
  traceConfig: { includedCategories: ['disabled-by-default-memory-infra'] },
  transferMode: 'ReportEvents',
})
await cdp.send('Tracing.requestMemoryDump', { deterministic: true, levelOfDetail: 'detailed' })
// periodic_interval 事件的 args.dumps.allocators，逐項 attrs.size.value 是十六進位位元組
```

要看的是 `malloc` ＋ `blink_gc`（樣式與 DOM 物件）與 `cc/tile_memory`
（光柵磚）。同一份傾印裡 `skia/sk_glyph_cache` 是 **0.9 MB**——字符點陣
從來不是這一頁的成本。

## 定律

合成頁：4,000 個 `<p>`，字級分散成 K 種，兩種堆疊各量一次（取兩輪最小）。

| 相異字級 K | 系統字堆疊 | 堆疊含兩個 109 片家族 | 5,120 位元組桶 |
| ---: | ---: | ---: | ---: |
| 1 | 47 MB | 47 MB | 0.1 |
| 20 | 47 MB | 73 MB | 22.4 |
| 100 | 83 MB | **243 MB** | **163** |

斜率：每種描述約 **1.6 MB**（系統字約 0.36 MB）。錢花在 5,120 位元組那個
配置桶上，也就是 Blink 為每一種 `FontDescription` 建的 **fallback list**：
堆疊裡有 218 片 `unicode-range` 字面，每一份清單就得攤開那 218 片。

**與載入無關**：229 個 `@font-face` 宣告只值 5 MB；載入 104 片切片、每片只
排一個字，只比零片多 11 MB。真正決定成本的是**堆疊裡宣告了幾片** ×
**頁面上有幾種相異描述**。

## 對照

首頁（首幀只排 1,657 個字）private footprint **543 MB**，apple.com 的
MacBook Pro 商品頁 **172 MB**。拆下來：

| 分項 | 首頁 | apple |
| --- | ---: | ---: |
| malloc | 249 | 67 |
| blink_gc | 151 | — |
| cc/tile_memory | 132 | 13 |
| skia 字符快取 | 0.9 | — |

把 `han.fonts.css` 裡**傳承／行書那 13 個 `@container` 區塊**拿掉（也就是把
切片家族從堆疊裡拿掉），樣式記憶體 548 → 275 MB。標點那 20 個區塊、16 個
`@property` 註冊、以及掛在 `:where(*)` 的複合宣告，**成本都是零**——合成頁
另外驗過：8,000 個元素各掛 138 個註冊自訂屬性、再加 66 條命中的
`@container style()`，一毛錢都沒多花。所以「容器查詢矩陣很大」不是問題，
「字族串裡有切片家族」才是。

## 於是怎麼省（兩個乘數，都不必碰字形）

成本 ＝ **相異描述數** × **每份 fallback list 的大小**，而後者 ＝ 堆疊裡
**宣告了幾片**。兩個乘數各有一刀，捨棄傳承字形不在選項裡——那是這個專案
存在的理由。

**其一，收斂字級刻度。**首頁 150 種描述 ＝ 42 種字級 × 27 種字族串，而
42 種裡有 24 種是碎值：

| 字級 | 元素數 | 來自 |
| --- | ---: | --- |
| 8.5px | 162 | 鉛字盤的 SVG `<text>` |
| 13.3333px | 74 | 表單控件的預設字級 |
| 11.998px | 45 | 報眉／作者行（rem × em 連乘） |
| 128.889px | 37 | 破折號柱 |
| 5.999px / 9.002px | 11 | 注音 `rt` |

`16.002px` 與 `15.998px` 在畫面上看不出差別，卻各要一份 fallback list。

**其二，切片更少更大。**攔截 ziano 的 CSS、把 109 片併成 N 片再送
（同一批真檔，只改 `unicode-range` 的分組），100 種字級下：

| 切片數 | 樣式記憶體 | 高出系統字地板 |
| ---: | ---: | ---: |
| 109 | 219 MB | ＋136 |
| 30 | 161 MB | ＋78 |
| 10 | 112 MB | ＋29 |
| 4 | 99 MB | ＋16 |
| 0（系統字） | 83 MB | — |

大致線性。代價是快取粒度：切片越大，讀者為一個沒用到的字付的位元組越多。
這是 ziano 那邊的取捨，不是 han.css 的。

## 給庫的使用者

這是 han.css ＋ ziano 這一套組合的通用成本，不是首頁獨有。文件應該說明：
**流體字級（`clamp()`／`vw`／連乘 em）會逐元素產生相異描述**，在切片字族
底下每一種都要價 1.5–2 MB。固定刻度、或在葉節點用 `round()` 收斂。另一半在字族側：切片的**片數**
直接乘進每一份清單，出片時要把它當成一個效能參數，不只是快取參數。

量測陷阱：把 CDN 的 `@font-face` 抄成行內 `<style>` 會讓 `src` 的相對路徑
對著 `about:blank` 解析，字體靜靜地沒載，於是量到的是系統字的數字（我因此
一度得到「片數不影響」的假結論）。要嘛保留 `<link>`，要嘛把 `src` 改寫成
絕對網址。
